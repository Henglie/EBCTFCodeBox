# Base64

> 对应 UI：左侧「Base 编码」→ `Base64`。所属：Base 编码族。

## L1 速查

**是什么**：把任意字节按「每 3 字节 → 4 个字符」转成纯 ASCII 文本的通用编码，是邮件、JSON、URL 参数里最常见的二进制搬运方式。它不加密，任何人都能解。

**参数表**：

| 参数（UI 名） | 类型 | 默认 | 取值说明 |
|---|---|---|---|
| URL-safe（+/ → -_） | 开关 | 关 | 开启后 `+`→`-`、`/`→`_`，用于 URL / JWT |
| 补齐 =（关闭即无 padding，如 JWT） | 开关 | 开 | 关闭后末尾不写 `=`，长度可能不是 4 的倍数 |
| 解码时移除非字母表字符 | 开关 | 关 | 解码前剥掉换行、空格等非 Base64 字符 |
| 严格模式（解码遇非字母表字符即报错） | 开关 | 关 | 与上一项互斥：开了它就不再静默剥离 |
| 自定义码表 | 文本 | `A-Za-z0-9+/` | 换掉 64 字符字母表（变种题用） |
| 显示所有 Base64 偏移 | 开关 | 关 | 展示同 CyberChef 的偏移视图 |
| 偏移展示：字母表 | 文本 | `A-Za-z0-9+/=` | 偏移视图使用的字母表 |
| 偏移展示：标注可变/填充字符 | 开关 | 关 | 在偏移视图里标出可变化位置 |
| 偏移展示：输入格式 | 下拉 | Raw | `Raw` / `Base64` |

**最小示例**：

```
输入：foobar
参数：默认
点「编码」→ 输出：Zm9vYmFy
```

## L2 详解

**操作全流程**：
1. 左侧分类选「Base 编码」→ `Base64`；
2. 原文粘进输入框，点「编码」得到 Base64；反向则粘 Base64 串点「解码」；
3. 解不出来先看是不是这三件事：① 串里混了换行（开「移除非字母表字符」）；② 是 URL 变种（开 URL-safe）；③ 是 JWT 段（关 padding）。

**算法原理**：把输入按 3 字节一组切开，24 位重新分成 4 个 6 位，每个 6 位值（0–63）查 64 字符表得到一个字符。不足 3 字节时补 0 位，并用 `=` 占位——所以 Base64 长度总是 4 的倍数，末尾 `=` 的个数表示缺了几个字节。

**常见坑**：
1. **URL-safe 与标准表不能混用**：标准表的 `+` `/` 在 URL 里会被转义成 `%2B` `%2F`，所以 JWT、短链用的是 `-` `_`。拿标准解码器解 URL-safe 串，会在含这两个字符处出错。
2. **padding 关掉后长度不再是 4 的倍数**：JWT 的每一段都没有 `=`，直接按 4 的倍数校验会误判成坏数据。
3. **换行是合法噪声不是错误**：邮件里的 Base64 每 76 字符换行，直接解会失败；开「移除非字母表字符」或先删换行。
4. **`=` 只是占位，不是数据**：解码时 `=` 的数量必须与最后一个字符的有效位匹配，多一个少一个都可能解出错误字节而不报错。
